# Развёртывание в Яндекс Облаке

Пошаговая инструкция для боевого запуска. Данные остаются на территории РФ — это
требование ч. 5 ст. 18 152-ФЗ для персональных данных граждан России.

## Что понадобится

| Сервис | Зачем | Конфигурация для старта |
| --- | --- | --- |
| Compute Cloud (ВМ) | Приложение | Ubuntu 24.04, Intel Ice Lake, 2 vCPU (гарантированная доля 100%), **4 ГБ RAM**, network-ssd 20 ГБ, не прерываемая, статический публичный IP |
| Managed Service for PostgreSQL | База данных | PostgreSQL 16, Intel Ice Lake, тип хоста standard, класс `s3-c2-m8` (2 vCPU / 8 ГБ), network-ssd 20 ГБ, 1 хост, без публичного IP |
| Object Storage | Медиа и бэкапы | Стандартный класс хранения, ~5 ГБ |
| Cloud DNS | Домен | Если домен обслуживается в Яндекс Облаке |

**Почему 4 ГБ RAM.** Цифра продиктована не нагрузкой, а сборкой: `next build` на
1–2 ГБ падает по нехватке памяти, а в рантайме Node занимает всего 200–400 МБ.
Если берёте машину меньше, добавьте swap-файл или собирайте образ отдельно.

**Почему 2 vCPU с гарантированной долей 100%, а не burstable (20%).** Burstable-ВМ
дешевле, но троттлинг после исчерпания накопленных тактов бьёт по p95-времени
ответа, а у сайта SEO-трафик — просадки на p95 портят и краулинг, и конверсию.
Второе ядро на практике достаётся не самому приложению, а TLS, отдаче медиа через
`/api/media/[id]` и ночному cron по подпискам — без него они конкурируют за то же
ядро, что и обработка запросов.

**Почему один хост базы, а не кластер.** Автоматические бэкапы и PITR в Managed
PostgreSQL доступны уже на одном хосте — их не нужно покупать через кластер.
Автоматический failover, наоборот, требует минимум двух хостов (а для честного
кворума — трёх) и заметно увеличивает счёт за базу. При этом приложение всё равно
крутится на одной ВМ без резервирования, поэтому кластер из трёх хостов не даёт
сквозной отказоустойчивости — базой самое слабое звено уже не является. Второй
хост стоит добавлять тогда же, когда появляется вторая ВМ с балансировщиком, а не
раньше.

**Почему `s3-c2-m8`, а не меньше.** Это самый младший класс из линейки `standard`.
Для базы, которая на старте весит около 10 МБ, 8 ГБ памяти — примерно
восьмисоткратный запас, избыточный по факту. Но смена класса на кластере из
одного хоста требует перезапуска с недоступностью, а при переходе на два хоста
`standard` понадобится всё равно — экономить один раз, чтобы потом пересаживаться
с простоем, смысла нет. Если экономия критична, дешевле burstable-класс
`b3-c1-m4`, с оговоркой, что Яндекс не позиционирует `b*`-классы для продакшена.

**Почему стандартный класс Object Storage, а не холодный/ледяной.** Картинки из
заметок читаются на горячем пути при каждом просмотре страницы без браузерного
кеша (см. «Исходящий трафик» ниже), а холодные классы хранения берут отдельную
плату за каждое извлечение объекта — при таком паттерне доступа она перекроет
экономию на хранении.

Postgres можно поставить и прямо на ВМ — это дешевле, но тогда бэкапы придётся
настраивать самостоятельно (`pg_dump` по расписанию в Object Storage). Для базы с
платежами и персональными данными управляемый кластер с автоматическими бэкапами
и PITR надёжнее.

## Исходящий трафик

Оценка ниже посчитана по продакшен-сборке с gzip — пригодится, чтобы выбрать
тариф и не удивиться при заполнении калькулятора Яндекс Облака.

Что качается при типичном визите:

- статика первого визита — 381 КБ (JS 264 КБ, шрифты 110 КБ, CSS 7 КБ), дальше
  отдаётся из браузерного кеша как immutable;
- страницы: главная 11 КБ, каталог 17,6 КБ, страница заметки 13–30 КБ,
  `sitemap.xml` 11 КБ, ответ `/api/search` 1,7 КБ;
- медиа: 30 объектов в среднем по 962 КБ (максимум 2,4 МБ); картинки есть у
  12 заметок из 56, в среднем по 2,3 штуки на заметку.

При модели 2,5 просмотра за сессию и 60% новых посетителей на визит выходит
≈1 МБ, из которых около двух третей — картинки. Отсюда оценка по месяцу:

| Визитов в сутки | Трафик в месяц |
| --- | --- |
| 100 | ~3 ГБ |
| 500 | ~15 ГБ |
| 1000 | ~30 ГБ |
| 5000 | ~150 ГБ |

Плюс 0,3–0,5 ГБ в месяц на обход поисковых роботов.

**Весь этот трафик идёт через ВМ**, а не через базу или бакет: `GET
/api/media/[id]` переливает байты через Node (см. CLAUDE.md, раздел «Медиа»), а не
редиректит на presigned-ссылку Object Storage. Поэтому исходящий трафик в
интернет у кластера PostgreSQL (он без публичного IP) и у бакета Object Storage
равен нулю — при заполнении калькулятора поле «Исходящий трафик» нужно указывать
только для ВМ, иначе трафик посчитается дважды.

Операции самого Object Storage — отдельная статья расхода: при 1000 визитов в
сутки это примерно 21 000 GET в месяц (каждая некешированная картинка — один GET
к бакету) и около 100 POST (загрузки через админку и импорт заметок).

Что меняет картину:

- **конвертация картинок в WebP** уменьшает медиа-трафик примерно вшестеро —
  визит с ~1 МБ падает до ~0,43 МБ;
- **CDN перед сайтом** имеет смысл ближе к 5000 визитов в сутки: он переносит
  отдачу медиа с ВМ на себя, а `Cache-Control: immutable` на `/api/media/*` для
  этого уже проставлен — дополнительных правок в коде не потребуется.

## Чек-лист перед созданием ресурсов

- **IP именно статический**, а не динамический — иначе после остановки ВМ адрес
  меняется, A-запись «уезжает», и Caddy не сможет выпустить сертификат (см.
  шаг 3 «Домен»).
- **ВМ и хост Managed PostgreSQL — в одной зоне доступности.** Иначе каждый
  запрос к базе получает лишние миллисекунды сетевой задержки. Каталог шлёт свои
  три запроса параллельно (`Promise.all`), так что задержка не утраивается, но
  ложится на время ответа каждой страницы.
- **Своп-файл 2 ГБ на ВМ** как страховка на случай, если `next build` всё-таки
  упрётся в 4 ГБ RAM.
- **Место на диске:** реально занимается 6–8 ГБ (`node_modules` — около 1 ГБ,
  каталог `.next` разрастается до 1,7 ГБ за счёт `.next/cache`). 20 ГБ хватает с
  запасом, но кеш сборок стоит время от времени чистить.

## 1. Сеть и база

1. Создайте облачную сеть и подсеть в одной зоне доступности (например `ru-central1-a`).
2. Создайте кластер Managed PostgreSQL 16: базу `secondbrain`, пользователя, пароль.
3. Разместите ВМ в той же подсети — тогда публичный доступ к базе включать не нужно.

Подключение к управляемой базе идёт по TLS с собственным удостоверяющим центром
Яндекса, поэтому на ВМ нужен его сертификат:

```bash
mkdir -p ~/.postgresql
curl -o ~/.postgresql/root.crt https://storage.yandexcloud.net/cloud-certs/CA.pem
chmod 0600 ~/.postgresql/root.crt
```

## 2. Виртуальная машина

Создайте ВМ с Ubuntu 24.04 и **статическим** публичным IP — динамический меняется
при перезапуске и ломает DNS-запись.

Группа безопасности:

| Направление | Порт | Источник |
| --- | --- | --- |
| Входящий | 80, 443 | `0.0.0.0/0` |
| Входящий | 22 | только ваш IP |
| Исходящий | все | `0.0.0.0/0` |

## 3. Домен

Создайте A-запись домена на статический IP машины и дождитесь распространения DNS —
Caddy не сможет выпустить сертификат, пока домен не резолвится в этот адрес.

## 4. Софт на сервере

```bash
sudo apt update && sudo apt install -y curl git

# Node.js 22
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs

# Caddy — обратный прокси с автоматическим HTTPS
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy

# Отдельный пользователь для приложения
sudo useradd -m -s /bin/bash app
```

## 5. Код и переменные окружения

```bash
sudo -iu app
git clone https://github.com/BigBabyDoc/SecondBrain.git ~/secondbrain
cd ~/secondbrain
cp .env.example .env
nano .env
```

Минимальный боевой `.env`:

```env
DATABASE_URL="postgresql://user:pass@rc1a-xxxx.mdb.yandexcloud.net:6432/secondbrain?sslmode=verify-full&sslrootcert=/home/app/.postgresql/root.crt"

AUTH_SECRET="<openssl rand -base64 32>"
NEXTAUTH_URL="https://ваш-домен.ru"
AUTH_TRUST_HOST=true

YOOKASSA_SHOP_ID="..."
YOOKASSA_SECRET_KEY="..."

SMTP_HOST="smtp.mail.ru"
SMTP_PORT="465"
SMTP_USER="second_brain_pediatra@mail.ru"
SMTP_PASSWORD="<пароль для внешних приложений>"
MAIL_FROM="second_brain_pediatra@mail.ru"

CRON_SECRET="<openssl rand -hex 32>"
```

Три вещи, без которых будет ломаться:

- **`AUTH_TRUST_HOST=true`** — за обратным прокси NextAuth v5 иначе отвергает запросы
  с ошибкой `UntrustedHost`, и вход перестаёт работать.
- **`NEXTAUTH_URL`** должен быть боевым `https`-адресом: он подставляется в ссылки
  из писем, в `return_url` для ЮKassa и в `sitemap.xml`.
- **`SMTP_PASSWORD`** для Mail.ru — это отдельный «пароль для внешних приложений»
  из настроек почты, а не пароль от ящика.

## 6. Сборка и запуск

```bash
npm ci
npx prisma migrate deploy
npm run build
```

> **Не запускайте `npx prisma db seed` на проде.** Пароли демо-аккаунтов лежат в
> открытом виде в репозитории. Сид намеренно отказывается работать при
> `NODE_ENV=production` без заданных `SEED_ADMIN_PASSWORD` и `SEED_DOCTOR_PASSWORD`.
> Администратора лучше создать вручную или один раз засеять со своими паролями.

Роль администратора выдаётся из консоли — страницы для назначения ролей в
интерфейсе нет. Обычный путь: человек регистрируется на сайте сам (тогда пароль
знает только он, а согласия записаны как у всех), после чего роль повышается:

```bash
sudo -iu app
cd ~/secondbrain
npm run admin:grant -- --dry-run user@mail.ru   # показать, что изменится
npm run admin:grant -- user@mail.ru             # применить
```

Если регистрация недоступна, недостающего пользователя можно завести сразу
админом: `ADMIN_PASSWORD=... npm run admin:grant -- --create --name="Имя" user@mail.ru`.
Пароль передаётся только переменной окружения — аргументы видны в `ps` и в
истории оболочки; согласий у такой записи не будет, их придётся принять при
первом входе. Роль лежит в JWT-сессии, поэтому уже вошедшему пользователю нужно
выйти и войти заново.

Скопируйте юнит и запустите сервис:

```bash
exit  # вернуться из-под пользователя app
sudo cp /home/app/secondbrain/deploy/secondbrain.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now secondbrain
sudo systemctl status secondbrain
```

## 7. HTTPS

```bash
sudo cp /home/app/secondbrain/deploy/Caddyfile /etc/caddy/Caddyfile
sudo nano /etc/caddy/Caddyfile   # заменить example.ru на свой домен
sudo systemctl reload caddy
```

Сертификат Let's Encrypt Caddy выпустит сам и будет продлевать автоматически.
HTTPS здесь обязателен: через него передаются пароли и персональные данные.

## 8. Ежедневная задача по подпискам

```bash
sudo cp /home/app/secondbrain/deploy/secondbrain-cron.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now secondbrain-cron.timer

# разовая проверка
sudo systemctl start secondbrain-cron.service
sudo journalctl -u secondbrain-cron.service -n 20
```

Без этой задачи истёкшие подписки не переводятся на бесплатный тариф, а
напоминания об окончании не рассылаются.

## 9. ЮKassa

1. В личном кабинете укажите вебхук `https://ваш-домен.ru/api/webhooks/yookassa`.
2. В разделе «Отправка чеков» выдайте разрешение работать с чеками через «Мой налог» —
   без этого чек по платежу не сформируется.

## 10. Проверка после запуска

- регистрация нового пользователя, письмо реально доходит до почты;
- переход по ссылке подтверждения открывает доступ к оплате;
- тестовый платёж проходит, подписка активируется, приходит чек;
- восстановление пароля работает;
- `https://ваш-домен.ru/robots.txt` и `/sitemap.xml` отдают боевой домен, а не localhost.

## Бэкапы

У Managed PostgreSQL автоматические бэкапы включены по умолчанию — проверьте
глубину хранения в настройках кластера. Если Postgres стоит на самой ВМ, настройте
ночной `pg_dump` с выгрузкой в Object Storage; база с платежами и персональными
данными без бэкапа — недопустимый риск.
